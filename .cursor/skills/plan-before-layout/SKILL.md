# План до верстки

Если тебе приходит задача чтото сверстать, например по фигме или по скрину, или задача крупная, то перед версткой всегда делай план. Сохраняй его в prompts/plans, и только потом предлагай начать верстку.

## Когда применять

Делать план, если верно любое:

- есть Figma, скрин, макет, референс блока;
- пользователь просит сверстать / сверстать блок / секцию / страницу / шаблон;
- работа трогает несколько файлов, новый компонент, новый контракт API или раскладку страницы.

Не применять к мелочи: опечатка, один класс, переименование, правка уже согласованного плана в коде после «начинай».

## Порядок

1. Собрать контекст (код, контракт бэка, скрин). Не выдумывать эндпоинты.
2. Уточнить развилки, которые меняют план (один-два вопроса).
3. Записать план в `prompts/plans/<slug>.md` (kebab-case, без даты в имени, если нет коллизии).
4. В ответе пользователю кратко изложить план и путь к файлу.
5. Явно спросить, начинать ли верстку. **Стоп.** Код не писать.

После «делай», «верстай», «поехали», «начинай» — выполнять сохранённый план. Если пользователь правит план — обновить файл в `prompts/plans`, снова предложить старт, не верстать.

## Файл плана

Markdown на русском. Без эмодзи. Ссылки на файлы репо — полным путём.

```markdown
# Краткий заголовок

## Цель
Что должно появиться на экране.

## Контракт данных
Роуты, JSON-ключи, что уже есть / что должен отдать бэк.

## UI
Блоки, поведение (клик, состояние), a11y (один h1, кнопки).

## Файлы
Какие пути создать или изменить.

## Не делать
Вне скоупа.
```

Не класть планы в `.cursor/plans` вместо `prompts/plans`. Cursor Plan mode не отменяет этот файл.

## Не делать

- Не начинать верстку в том же ходе, что и план.
- Не считать `prompts/plans` документацией для сторонних клиентов (`pattern-front.md` и скилл `update-client-patterns` не трогать из‑за плана).
