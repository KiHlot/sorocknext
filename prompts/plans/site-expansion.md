# Расширение сайта: сущности, архив, тесты, журнал

## Цель

Перевести sorock.ru из контентного сайта (новости/статьи/рецензии) в медиа-справочник:
сущности (альбом/фильм/клип/концерт), архив старых новостей, интерактивные тесты,
авторский журнал с произвольной версткой. Сохранить SEO и не сломать существующие URL.

## Ключевая идея — два слоя контента

Разделить всё, что есть и появится, на два слоя с разной логикой:

- **Сущности** — стабильные объекты каталога. Мало полей, жёсткая структура,
  перелинковка, живут годами. `album`, `film`, `clip`, `concert`.
- **Контент** — статьи *про* сущности и вокруг них. Обычные посты.
  `news`, `reviews`, `autors`, `cool`, `nocommerce`, `rock-data`, `journal`, `site-archive`.

Контент ссылается на сущности через Post Object-поле. Сущность — источник истины
по артисту, году, лейблу, стране. Сейчас альбом-инфа (`albom_info`, `music_code`)
зашита внутри рецензии — это потом надо развязать (см. «Открытые вопросы»).

- `news` — остаётся, но ужимается до актуальных новостей.
- `reviews`, `cool`, `autors`, `nocommerce`, `rock-data` — без изменений.

  `entity_event_date`, `entity_tickets_url`.
- `clip`: `entity_artist`, `entity_video_code`.

### Новые контентные

| CPT | Назначение | URL |
|---|---|---|
| `site-archive` | Архив старых новостей (см. миграцию) | `/archive/{slug}` |
| `journal` | Журнал: длинные статьи с блочной версткой | `/journal/{slug}` |

Сущности **не** попадают в `in_latest_posts`, **не** ищутся в общем поиске по умолчанию,
живут на своих архивах. Контент — как сейчас.

## Миграция news → site-archive

Цель — убрать из «актуального» те stale-материалы, но сохранить URL и SEO.

**Что нужно решить перед миграцией:**

1. **Критерий отбора.** Пресеты: по дате (`< N лет назад`), по метке `archived`,
   по рубрике, вручную. Предлагаю комбинированный: по дате + ручной флаг `do_not_archive`.
   Скидываем в JSON-файл список ID к переносу — редактор смотрит и подтверждает.

2. **URL-стратегия.** Два варианта:

    - **A. Меняем URL.** Старое `/news/{slug}` → новое `/archive/{slug}`.
      Нужен 301-редирект на каждый пост. SEO-вес переносится корректно.
      Минус: много редиректов, Yoast-карта переезжает.
    - **B. URL не меняется.** `register_post_type('site-archive', ['rewrite' => ['slug' => 'news']])`,
      а сам `news` переименовывается в `news-current` со слагом `/news-current/`.
      Плюс: ссылки живут, редиректов нет. Минус: семантически `/news/` = архив,
      это неочевидно, и админ-раздел придётся переучивать.

   Рекомендую **A** — привычнее для SEO, чище семантически. Для 5000+ постов
   редиректы кладём в `.htaccess` или в middleware Next.js (карта slug → slug
   в JSON, отдаётся через `/archive/get-redirect-map`).

3. **Порядок миграции:**
    - Бэкап БД и файлов.
    - Скрипт: `UPDATE wp_posts SET post_type = 'site-archive' WHERE ID IN (...)`;
      пересчёт term relationships, если таксономии у архивного CPT отличаются.
    - Регенерация rewrite rules (`flush_rewrite_rules`).
    - Проверка всех старых URL: 301 на новый адрес.
    - Обновить Yoast sitemap (он пересоберёт сам, но проверить).
    - Проверить, что в ленте `in_latest_posts` архива нет.

4. **SEO-настройки архивного CPT:** `noindex, follow` — контент старый, но ссылочный вес
   внутри сохраняем; либо оставить индексируемым, если хотим «долгоиграющий» трафик
   на конкретных материалах. Обсудить.

## Таксономии

Сейчас все CPT сидят на общей `category`. Это работает для контента, но для сущностей
не подходит.

Предлагаю:

- **Контент** — `category` и `post_tag` как есть (архивные новости — тот же набор).
- **Сущности:**
    - `genre` — **общая** таксономия для `album`, `film`, `clip`, `concert`
      (`rock`, `metal`, `punk`, `jazz`, ...). Единый справочник жанров.
    - `country` — общая таксономия стран (или оставить ACF-поле `event_country`).
    - `label` — только для `album`.
    - `artist` — только для `album`/`clip`, либо общая для всех сущностей
      (артист как сущность, тогда отдельный CPT `artist`).
    - `director` — только для `film`.

**Важный выбор:** `artist` — это отдельный CPT (сущность со своей страницей,
дискографией, концертами) или таксономия? Если планируется страница артиста —
только CPT. Таксономия + ACF-группа даст ту же функциональность, но менее удобно
для связей «артист → альбомы → клипы → концерты».

Рекомендую **отдельный CPT `artist`** — это третья сущность, самая важная для
перелинковки. Даже если сейчас не очевидно, потом пригодится.

`category` для сущностей **не используем** — иначе смешается с рубриками контента.

Существующие `categories_config` в `Site_Config` разбиваются на:
`content_categories_config` и `entity_taxonomies_config`.

## Тесты

CPT `test` + ACF Flexible Content для вопросов. Структура теста:

- ACF-группа `test_meta`: `test_intro` (заголовок, описание, обложка),
  `test_result_tiers` (repeater: `tier_key`, `tier_title`, `tier_description`, `tier_image`).
- ACF Flexible Content `test_questions`: каждый блок — вопрос.
    - `question_text`, `question_image` (опционально),
    - `question_answers` (repeater): `answer_text`, `answer_score_map` (JSON-like
      поле или по одному числу на каждый tier).
- Frontend: `'use client'`-компонент, `useState` по ответам, прогресс,
  финальный экран с tier-результатом. Кнопка «Поделиться» (copy link).

**Результаты не сохраняем.** Портал публичный, авторизация будет удалена.
Если позже понадобится аналитика — отдельный эндпоинт + таблица, но не сейчас.

Первый тест — «Какую гитару выбрать», второй — «Какой жанр мне подходит»:
один технический (категории/параметры), второй — про вкус (tier'ы).

## Журнал

CPT `journal` + ACF Flexible Content. **Никакого общего шаблона** — редактор
собирает статью из блоков, как в конструкторе.

Фронт — **реестр блоков**: ACF `acf_fc_layout` → React-компонент.
Первый набор блоков:

- `text` — rich text.
- `heading` — h2/h3 с якорем.
- `image_full` — картинка на всю ширину с подписью.
- `image_text` — две колонки: картинка + текст.
- `gallery` — сетка/Swiper.
- `quote` — крупная цитата.
- `video_embed` — видео (YouTube/VK).
- `music_embed` — музыкальный плеер (`mountMusicEmbed` уже есть).
- `timeline` — хронология (repeater: год + событие + опциональное фото).
- `related_posts` — блок связанных статей.
- `cta` — кнопка/ссылка.

URL — `/journal/{slug}`. Хром — без сайдбара, полноширинный layout.
Метаданные — через Yoast, как у остальных постов.

Планирую вынести фронтовый реестр в `src/components/blocks/journal/` и
подключать через `JournalBlockRegistry.tsx`. Новый блок = один файл + регистрация.

## Влияние на фронтенд

- Роут `(site)/[postType]/[slug]` остаётся, но `page.tsx` выбирает шаблон
  по `postType`: `PostTPL` / `EntityTPL` / `JournalTPL` / `TestTPL`.
  Внутри — switch.
- Нужен `generateStaticParams` для новых типов (сущности — из бэка,
  как остальные посты). ISR через `revalidate`.
- `Site_Config::$post_types_config` — расширить полями:
  `is_searched`, `in_latest_posts`, `is_entity`, `tpl` (имя шаблона).
- `src/api/post/types.ts` — типы сущностей (`AlbumModelIF`, `FilmModelIF`, ...).
- Сайдбар: на страницах сущностей и журнала — свой (или без него).
- Хлебные крошки: `/albums` → `/albums/{genre}` → `/albums/{slug}`.
- JSON-LD: для сущностей — `MusicAlbum`, `Movie`, `MusicEvent` через
  `next/script` или компонент `<StructuredData />`. Yoast это не даст.

## Порядок этапов

Скоуп большой, делать в четыре захода:

1. **Этап 1. Архив новостей.** Миграция + редиректы + SEO. Небольшой по коду,
   но самый рискованный. Делать первым, пока сайт стабилен.
2. **Этап 2. Сущности.** `artist` + `album` + `film` + `clip` + `concert`.
   Таксономия `genre`. CPT + ACF + эндпоинты + TPL. Самый долгий.
3. **Этап 3. Тесты.** CPT + ACF + клиентский компонент. Быстро, эффектно.
4. **Этап 4. Журнал.** Flexible Content + реестр блоков на фронте.
   Делать последним — самый тяжёлый с точки зрения UI-вариативности.

Между этапами — заливка, проверка, отдельный PR.

## Риски

- **SEO.** 5000+ редиректов, если что-то потеряется — падение трафика.
  Обязательно проверить: `.htaccess`-правила не конфликтуют, Yoast sitemap
  пересобрался, старые URL отдают 301, а не 302/404.
- **Таксономии.** Переезд постов между типами и смена набора таксономий могут
  «потерять» term relationships. Нужны скрипты + dry-run.
- **Кэш.** ISR на новостных страницах после миграции — принудительный revalidate
  через `revalidateTag` или деплой новой сборки.
- **Производительность.** Сущности с большим числом повторителей могут тормозить
  при `get_top_album_model()` — кэшировать ACF-чтения.
- **ACF Flexible Content.** Много вариантов блоков → много фронтовых компонентов.
  Ошибка в одном ломает всю статью. Добавить error boundary на уровне блока.
- **Совместимость.** Пока не развязаны `albom_info` внутри `reviews` и новая
  сущность `album` — двойной источник истины. Решить до старта этапа 2.

## Что ещё стоит рассмотреть

- **Общий поиск.** Сейчас поиск — по всем `is_searched` типам. С сущностями надо
  решить: сущности в общий поиск или отдельно? Я бы сделал отдельный блок результатов
  «Альбомы», «Фильмы», «Артисты» в выдаче.
- **Sitemap-сегментация.** Yoast даёт один `sitemap_index.xml`. Для новых типов
  с большим объёмом — отдельные `news-sitemap.xml`, `album-sitemap.xml`.
  Google уважает `news`-специфичный формат.
- **View counts.** У сущностей появляется смысл считать просмотры (`mpf_page_views_count`
  уже есть). Пригодится для «популярных альбомов».
- **Рекомендации.** «Похожие альбомы» можно тянуть по пересечению `genre`
  и одного `artist`. Это дешёвый, но полезный блок.
- **RSS.** Отдельные фиды по `news`, `journal`, `test`.
- **Публикация.** Рассмотреть «editorial workflow»: черновик → review → публикация.
  Сейчас WP умеет это из коробки, но под новые типы стоит подкрутить capabilities.
- **Связь сущностей с рецензиями.** Сейчас в рецензии зашита своя `albom_info`.
  Правильнее — рецензия ссылается на `album` через Post Object, а `album` — источник.
  Это большая переделка. Обсудить, делать ли сразу или отложить.
- **Frontend sitemap.** Next.js `sitemap.ts` сейчас, вероятно, не используется
  (Yoast с WP отдаёт). Проверить, что финальный sitemap — один источник.
- **Редиректы в Next.js.** Если бэк отдаёт карту старый→новый slug, `next.config.ts`
  `redirects()` или middleware. Предпочтительнее — на WP, чтобы Google видел 301
  с исходного хоста. Обсудить.
